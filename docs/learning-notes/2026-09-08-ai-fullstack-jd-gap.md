# AI 全栈岗位：从后端出发的补齐清单

## 结论

保留 Java 后端主线，优先补 JavaScript/TypeScript、React 和端到端联调能力，再按目标 JD 补 Next.js。不要同时铺开 Vue、Go、Node.js 后端和多个 AI 框架。

“AI 全栈”并非统一标准：有的强调借助 AI 编程跨端交付，有的强调开发 AI 应用；实习岗位也分“已有一端基础、接受拓展”和“已经能独立完成前后端”。以下是小样本对照，不据此推算市场占比；“大厂/中厂”也不作严格规模分类。

## 当前项目可以证明什么

按“项目导学”的证据核对方式，区分源码事实与个人掌握。以下是本轮静态核对，没有启动服务或运行新测试。

- `agent/app/static/commerce-demo.html` 第 174–178 行已有浏览器请求封装；第 219–227 行用原生 DOM 创建商品卡片。
- `agent/app/static/index.html` 第 2387、2393、3098 行已有流式解码、读取和聊天流接口调用。
- 项目已有 Java/Spring 后端、Python/FastAPI 和 CI 配置，不宜简单列为“从零补后端、Python、CI”。
- 本轮项目文件检索未找到可据以证明 React/TypeScript 工程化的前端项目；现有页面主要是原生 HTML/CSS/JavaScript。只能说明这份项目材料的证据缺口，不能断言用户在别处没有前端经验。
- 页面能运行、代码由 AI 辅助生成，不自动等于本人能独立设计组件、排查联调问题或完成部署。

## 建议补齐顺序

下面是结合 JD 与现有项目提出的学习拆分，不是每条 JD 都逐字要求这些细节。

| 优先级 | 知识 | 能独立完成的最小结果 |
|---|---|---|
| P0 | HTML/CSS/JavaScript → TypeScript | 写响应式页面，理解异步请求，给订单/明细/分页响应定义类型 |
| P0 | React | 组件、props/state、Hooks、表单、路由；做商品卡片与订单列表，不只是粘贴生成代码 |
| P0 | 浏览器与接口联调 | 用 Network 定位问题，处理 Cookie、鉴权、CORS/CSRF、加载/空数据/失败状态与重复提交 |
| P1 | AI 应用交互 | 解释并维护已有 SSE 展示、取消/失败处理、工具执行进度和写操作确认；取消展示不等于撤销业务操作 |
| P1 | 测试和交付 | 理解依赖安装、构建、环境配置、前端与端到端测试，能部署并排查页面到后端的故障 |
| 按 JD 补 | Next.js；Python/FastAPI 的个人熟练度 | React 稳定后再理解服务端/客户端边界；能够修改和调试已有 Python 接口，不另起多套后端 |

AI 编程工具使用应有可验证能力：能说明需求、读懂修改、复现错误、补测试并审查结果。工具名称本身不能替代工程能力。模型训练、多个前端框架和多门后端语言均不设为本轮统一前置条件。

## 最小实践建议：沿用订单查询主题

建议下一次经用户确认后，从一个 React + TypeScript 的“我的订单”页面开始：接现有分页接口，展示订单与多商品明细，支持继续加载、空列表、失败重试、登录失效，并防止旧请求覆盖新状态。随后再拓展登录、商品和已有 AI 流式交互。

验收看用户能否亲自解释组件拆分、游标传递、请求/响应、错误处理，并独立修改一个功能、跑通测试和部署。只建议实践，当前没有改造页面、后端或 Agent 架构。

投递策略：先关注“后端有专长、接受跨端拓展”的实习岗位；对明确要求已有 React/Next.js 熟练度、独立全链路交付的岗位，先补上述证据。毕业年份、实习时长、地点和是否仍开放需逐岗核验，不能由技术匹配代替。
