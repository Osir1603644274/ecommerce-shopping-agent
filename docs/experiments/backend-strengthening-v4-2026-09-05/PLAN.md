# 后端强化 V4：多商品、按数量退款与对账

状态：实施和审计中；不覆盖 V1/V2/V3 原件，不依赖 Agent。

## 业务范围

- 新增购物车下单，旧单商品 API 保持兼容；仅 PRODUCT，重复 SKU 拒绝，同一组商品逆序仍为同幂等请求。
- 优惠用整数分和最大余数法分摊，稳定商品排序处理平局；分批按数量退款须最终精确等于对应实付，不因四舍五入多退或少退。
- 本阶段支持从未派发的新购物车按数量退款；未知、已开始派发、已出库继续拒绝不安全的自动退款。旧整单与新部分退款入口不混用。
- PROCESSING 退款将任务置 REFUND_HOLD，只有匹配的持久回执可以恢复数量和余额；剩余商品生成新的不可变仓库命令版本，旧版本留存，fence 必须为 0。
- 本地退款模拟回执和业务对账使用独立事务，验证“回执已提交、业务更新失败”后主动对账。不是接入真实支付网关或物流。

## 审查与实际验证

1. 独立代码审计与金额代数验证；常规 Java 测试及无测试外层事务的并发/回滚测试。
2. 新 V4 数据卷先运行 V15 后端种下旧单，再执行 V16，验证迁移和旧订单兼容；两个 Java 实例使用同一真实 MySQL/Kafka。
3. 新购物车不足库存时订单/所有行库存/优惠/Outbox 同时回滚。
4. 707 分商品、5 分优惠，分摊 2/3 分；实付 702 分按 101+100+501 分全退，余额和库存必须精确守恒。
5. 退款重复/冲突/越权/超额、回执缺失/篡改、业务 Outbox 失败、12 个并发重复对账；保留修复前 MySQL REPEATABLE READ 失败与修复后新 attempt。
6. 部分退款后仅剩余数量出库、反序多商品并发无死锁、已领取/已出库拒绝退款；用数据库和独立 SQLite 仓库逐单关联。

默认关闭履约时新购物车写入拒绝，避免创建无退款路径的订单；不改变全局默认。真实 MySQL 复现优先于 H2 推断；H2 通过不自动证明 MySQL 默认隔离级别行为。
