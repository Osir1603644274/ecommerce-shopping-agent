### 2026-08-06：项目方向与 Agent Runtime 设计

**今日学习与讨论**

- 明确记忆与 Context 的关系：记忆是可持久化的信息来源，Context 是当前请求从系统规则、当前输入、短期/工作记忆及少量相关长期记忆中选择出来的运行时输入。
- 修正“短期记忆多放、长期记忆少放”的绝对表述：进入 Context 的多少应由相关性、优先级和安全性决定；长期稳定硬事实可能比近期闲聊更重要。
- 明确当前项目首期只做任务工作记忆，不做跨任务用户画像；Redis 是短期状态的一种存储实现，不等同于记忆概念本身。
- 识别单一 ContextPack 原封不动提供给所有组件的问题，形成“权威 ContextPack + Planner/Executor/Validator/Replanner/FinalAnswer 专用 ContextView”的设计。
- 明确外部工具不接收完整 Context，只接收经过 Schema 校验的最小参数；ContextView 必须携带相同的 `taskId`、`taskRevision` 和 `contextHash`。
- 对 AI 生成的 Agent Runtime 实现进行了独立验收，发现 ContextPack、BM25 Manager、Critic、Replay 和 Trace 多处只有模块或单测、没有接入真实主链，因此拒绝“所有任务完成”的结论，并把后续范围收敛为最小闭环。

**关键认知变化**

- Agent 工程能力不能通过堆叠 Memory、Multi-Agent、Critic 等名词证明，必须形成“上下文进入真实执行链路 → Trace 可观察 → Replay 可复现 → 评测能够比较”的闭环。
- ContextPack 更适合作为某个任务版本下的权威快照；不同组件应读取确定性投影出的最小 ContextView，而不是共享一份过大的提示词。
- 测试数量增加不等于能力已经上线。验收时必须检查真实调用方、启动生命周期、数据类型、失败路径和端到端行为。
