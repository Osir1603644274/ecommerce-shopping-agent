# 后端强化 V2：混合负载与数据库锁等待结果

- 日期：2026-09-05；结论：`BOUNDED_MIXED_WORKLOAD_AND_LOCK_RECOVERY_ACCEPT / HOLD_PRODUCTION_DEFAULT`。
- 在同一物理机的四组配对中，批查版分页 P95 变化率的中位数为 **−47.95%**，P99 为 **−34.65%**；分页观测请求/秒变化率中位数 **+91.61%**。
- 主要配对及锁阻塞场景共 **17,988 次 HTTP 请求、1,311 笔订单、0 HTTP 错误**；已支付订单各一条出库记录，取消订单无出库，库存和预占均核对一致。
- 本轮未修改生产 Java 业务源码。新增了混合负载、观测、对照分析和测试认证续期工具；独立 V2 服务及仓库进程已停止，数据卷和原件保留。后端不依赖 Agent 完成验证。

## 1. 比较对象与执行范围

基线是从 V1 已验证源码重建的 **N+1 控制实现**：只把 `OrderPageService.page` 中的明细批查替换为逐单查询，保持同一个 HTTP 接口、游标、20 单一页、鉴权、交易及履约逻辑。它不是原历史版本。唯一变更见 控制补丁（本地材料：`evidence/query-control.patch`），版本依据见 源码清单（本地材料：`evidence/source-manifest.json`） 与 JAR 清单（本地材料：`evidence/jars.json`）。主工作区后端源码、测试和工程文件共 326 项，与实验准备时哈希相同。

- JDK 17.0.19；MySQL 8.4.9；Kafka 3.9.1；本地支付与持久化仓库模拟器。
- 后端 1 CPU、768 MiB、Java 堆 384 MiB；Hikari 最大/最小连接数为 4；MySQL/Kafka 各上限 512 MiB。具体配置见 独立 Compose（本地材料：`evidence/compose.validation.json`）。这是验证配置，未修改业务默认。
- 每次应用重建后预热 40 次第一页读取；4 个读取线程、2 个写入线程，各阶段运行 30 秒。写入交替执行“创建→支付→模拟回调”和“创建→取消”。这是闭环客户端，实际读写比例随响应速度变化，不是固定 80/20 或固定到达率负载。
- 所有阶段读取相同的 10,000 单不可变 fixture；写入账号/商品每阶段独立，库存均从 100,000 开始。两臂共同访问的 **336 页**内容哈希一致；共访问 500 页，不能将其都算成跨臂比较页。

控制版有意违反“两次 Mapper 查询”的性能合同。其余语义测试首次因方法筛选拼写错误只执行 **4 项**，随后按正确方法名补跑 **1 项**，均通过；两批原件分别在 首次测试（本地材料：`evidence/control-test-reports`） 和 遗漏项补跑（本地材料：`evidence/control-missing-test-reports`）。不声称控制版通过性能合同或全量 216 项测试；后者属于 [V1 的既有证据](../backend-strengthening-v1-2026-09-04/FINAL_RESULT.md)。

## 2. 四组主要对照

以下 P95/P99 只统计订单分页请求。最后一列为分页的观测请求/秒；完整的创建、支付、回调、取消和总请求数据均在 分析结果（本地材料：`evidence/analysis-attempt001.json`） 的 `byOperation` 与逐请求原件中。

| 配对与次序 | P95 ms：N+1 → 批查 | P99 ms：N+1 → 批查 | 分页请求/秒：N+1 → 批查 |
|---|---:|---:|---:|
| 1：N+1→批查 | 205.41 → 107.53 | 296.98 → 196.30 | 33.71 → 66.19 |
| 2：批查→N+1 | 205.52 → 106.37 | 295.99 → 191.22 | 32.30 → 62.04 |
| 3：批查→N+1 | 193.53 → 98.79 | 214.41 → 108.14 | 44.04 → 79.35 |
| 4：N+1→批查，attempt002 | 201.37 → 109.16 | 287.16 → 193.26 | 33.85 → 64.70 |

表中变化率先逐对计算 `(批查/N+1 − 1) × 100%`，再取四对中位数，不是把所有请求混成一个 P95。分页 P50 变化率中位数为 −24.98%；第三对 P50 的波动明显，全部样本保留。

主要八个阶段共 **15,457 次请求、1,164 单**，其中 584 单支付、580 单取消；HTTP 错误均为 0。每阶段在负载结束后等待自身履约终态并核对库存，观察到的最大等待为 **8.344 秒**。这不构成生产积压恢复时限承诺。

### 第四对为何重跑

初始测试夹具只保存 15 分钟 access token，没有保存 refresh token。专用账号续期维护与第四对批查 attempt001 的计时窗口重叠 **1.272 秒**，额外认证请求不属于登记负载。因此按 [计划中的修订说明](PLAN.md) 保留两臂 attempt001 作为附加结果，另做完整第四对 attempt002；前三对和锁场景未重跑。

选择依据是协议外操作的时间戳，不是结果优劣。选择清单（本地材料：`evidence/phase-selection.json`） 明确列出主要/附加原件；分析器会拒绝把与认证维护重叠的阶段放进主要比较。附加两臂本身为 3,758 请求、290 单、0 HTTP 错误，原件仍在 原 N+1 阶段（本地材料：`evidence/pair4-nplusone-attempt001`） 和 原批查阶段（本地材料：`evidence/pair4-batch-attempt001`）。

## 3. 三秒库存行锁阻塞

在批查版 30 秒混合负载的第 10 秒，仅对该阶段专用商品的库存记录持有排他锁，实际持锁 **3.005 秒**，随后回滚释放。未锁主项目数据或其他阶段商品。

| 观察项 | 实际结果 |
|---|---|
| HTTP 与业务 | 2,531 请求、147 单、0 HTTP 错误；73 单支付、74 单取消，库存可用 99,927、预占 0、已售 73 |
| Hikari | 最大连接数 4；采样活跃连接峰值 4、等待连接峰值 6，连接超时计数为 0 |
| MySQL | 采样 `data_lock_waits` 峰值 3；阶段累计行锁等待增加 78 次、6,526 ms |
| 长尾请求 | 最慢支付回调 **3,286.535 ms**；该请求在注入前开始、持锁期间等待 |
| 整体 P99 | **280.863 ms**；少量三秒长请求没有进入整体 P99，不能只看这个分位数判断无阻塞 |
| 解除阻塞 | 锁释放后约 **0.285 秒**的首次采样看到数据库等待数为 0；这是采样分辨率内的观察，不是精确恢复时延 |
| 后台收尾 | 停止负载后约 **4.453 秒**完成该阶段履约终态核对；每个支付单一条出库，取消单无出库 |

原件：注入时间（本地材料：`evidence/row-lock-attempt001/injected-lock.json`）、逐请求数据（本地材料：`evidence/row-lock-attempt001/requests.jsonl`）、Prometheus 与 MySQL 原始采样（本地材料：`evidence/row-lock-attempt001/observations.jsonl`）、逐单不变量（本地材料：`evidence/row-lock-attempt001/business-invariants.json`）。6,526 ms 是多个等待的累计值，不等于整个系统停止了 6.526 秒。未提供的 `Innodb_deadlocks` 状态项没有被填成零。

## 4. 积压、可靠履约与测试工具修复

在正常混合负载的首个阶段也观察到：Hikari 等待峰值 5、履约 READY 积压峰值 23、内存队列峰值 14，队列拒绝计数从首次采样的 1 增至 2。持久任务继续保留并完成，说明“有拒绝/积压”和“任务丢失”必须分开判断。该阶段停载后的终态等待为 7.125 秒，原件见 第一阶段（本地材料：`evidence/pair1-nplusone-attempt001`）。

包括附加阶段在内，全部实测共 **21,746 请求、1,601 单**；802 单支付、799 单取消，HTTP 错误为 0。最后 Kafka 履约组已提交 offset 与日志末尾均为 **3,202，lag=0**，见 消费者证据（本地材料：`evidence/kafka-final-offsets.log`）。这补充了负载下的自然积压证据，不能代替后续受控乱序、停消费或多实例实验。

测试工具已修复为保存 refresh token，并在后续阶段开始前通过真实 `/api/auth/refresh` 轮换。连续两次实际 HTTP 刷新通过，读取用户、10,000 单数量和 fixture 哈希保持相同，见 刷新修复检查（本地材料：`evidence/fixture-refresh-check-attempt001/result.json`）。首次旧夹具缺凭证的修复仅作用于已验证的 V2 合成账户；重启期间的首次断连与随后成功事件也保留，没有修改签名密钥、TTL、角色或 token version。

**版本区别**：实测负载脚本 SHA256 为 `15f2f4d432ee0507919241f46b081757296f77e0e20aa83c92675887fd2898ef`，保存在 执行脚本快照（本地材料：`evidence/executed-scripts/mixed_workload.py`）；续期修复后的交付版本为 `a1540284732d280610dcff62699f427bbf58bc00e666f0573456510cb17b8f86`，保存在 交付脚本快照（本地材料：`evidence/delivered-scripts/mixed_workload.py`）。修复后验证了刷新分支，未将旧测量冒充新脚本完整重跑。实际环境以保存的 Compose 为准。
