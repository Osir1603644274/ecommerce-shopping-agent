# 后端强化 V2：混合负载与数据库锁等待

- 登记日期：2026-09-05；承接 V1 已交付的分页、批查和可靠履约。
- 授权来源：用户要求当前任务完成后按四条拓展主线继续推进；本轮先补性能工程缺口。
- 运行状态：准备完成，尚未将计划项目判为通过。正式结果另写 `RESULT.md`，每个失败 attempt 原件保留。

## 固定比较口径

1. 使用已验证的批查 JAR；另在独立副本中只将 `OrderPageService` 的明细读取改为逐单查询，构建 N+1 控制 JAR。生产源码不回退。控制版是同接口重建对照，不是原历史版本。
2. 两臂均为相同游标、20 单一页、相同鉴权及交易/履约逻辑。控制版有意违反“两次 Mapper 查询”的优化合同，因此只运行其余 5 项分页/权限语义测试；不声称控制版通过了优化合同或全量 216 项测试。
3. 同一份不可变 10,000 单读取 fixture；每阶段写入账号和商品独立，库存均从 100,000 开始。读取内容按页 SHA256 交叉核对。
4. 每次启动后预热 40 次第一页读取；4 个读取线程、2 个写入线程运行 30 秒。写入交替执行“创建→支付→模拟回调”和“创建→取消”；实际读写比例由逐请求记录给出。
5. 四对固定顺序：N+1→批查、批查→N+1、批查→N+1、N+1→批查。每次独立启动应用；记录全部样本和逐对差异，不只选最佳结果。
6. 另用批查版进行 30 秒混合负载：第 10 秒仅对本阶段专用商品库存持有 3 秒排他锁，随后回滚释放。观察连接池等待、数据库锁等待和恢复；不修改业务库或真实订单。

## 环境与证据

- 独立 Docker 项目 `backend-strengthening-v2`，新数据卷；V1 服务及正式证据保持原样。端口沿用空闲的 38080/33316/36389/39092/19091，不能与 V1 同时启动。
- 后端 1 CPU、768 MiB、JDK 17、堆上限 384 MiB；Hikari 最大/最小连接数为 4。MySQL/Kafka 各上限 512 MiB。以上是验证配置，不修改生产默认。
- 后端、MySQL、Kafka、持久仓库模拟器组成实际链路；不调用 Agent 或模型。
- 保存 JAR/源码/脚本身份、控制补丁、语义测试、每请求耗时与页内容哈希、原始 Prometheus、MySQL 锁等待计数、履约/Outbox 积压以及每单最终状态。
- 每阶段核验已支付订单各一条出库记录、取消订单没有出库、库存总量守恒、预占归零。HTTP 成功本身不能代替业务一致性验收。

## 结论限制

这是同一物理机的闭环客户端负载；并发 Context、JIT、缓存与数据表增长无法完全控制。四对仅作本机描述性对照，不认定生产 QPS、开放到达率下的容量或普遍性能优势。支付/仓库仍是本地模拟，未对接真实支付和物流。

本轮补齐后继续核对真实乱序/积压、多实例领取，再推进支付超时竞争、退款对账和业务扩展；不能将本轮视为四条主线全部完成。
