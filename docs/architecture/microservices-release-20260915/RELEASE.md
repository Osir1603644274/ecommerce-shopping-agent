## 交易协议

1. 交易先持久化库存 TRY 意图，再发送稳定命令 ID；库存端在本地事务中保存命令回执与库存变化。
2. HTTP 回包丢失时查询原命令回执；未知状态不等同于业务失败，不自动换键重复购买。
3. 支付确认、取消释放与退款命令进入交易本地持久日志 / Outbox；库存不可用时保留待恢复状态。
4. 订单事务回滚或 JVM 崩溃后，恢复器在订单行锁下核对是否真正未提交，再释放孤儿预占。已释放终态阻止迟到预占。
5. 库存确认尚未完成时不领取仓库发货任务。模拟支付和仓库回执分别验证，不用 HTTP 200 代替库存落账证明。

## 正式迁移中发现的问题

首次下单的库存外键错误指向旧 schema，但稍后查询数据字典已显示新 schema。这说明只读元数据验收不足以证明写入可用。其间 MySQL 于 `2026-09-15T14:26:35Z` 重启，随后同一原确认 / 幂等键恢复建单成功；不能把这一现象宣称为某个已确定的 MySQL 缺陷根因。

加固措施：跨 schema 移表后，在保持外键检查开启的情况下，以原子 ALTER 重新绑定小型预占表外键；启动器增加真实 INSERT 后回滚的正反检查：已有库存必须可引用、不存在的库存必须被拒绝。没有删除业务数据、关闭外键或手动修改库存金额。`FK-MIGRATION-REGRESSION-ce777d93.json` 验证该 DDL 与约束行为；小型复现实验没有复现最初的瞬态错误，明确保留这一限制。`LIVE-FK-REBIND.json` 和 `LIVE-INVENTORY-FK-PROBE-*.json` 记录正式处理及写入检查。

另有两次验收脚本断言错误：支付模拟接口实际包装为 `success/data`，业务状态冲突实际可能返回 422 而非 409。根据接口源码修正断言后重新完整运行；失败尝试保留，不计入通过。

## 恢复与限制

日常入口：`pwsh -File scripts/merged-commerce.ps1 start`，检查使用 `health`。已有微服务发布清单时不允许自动恢复旧 Java 单体，因为表所有权已迁移；禁止将历史备份直接覆盖当前库来“回滚”。

全部原始业务表计数在迁移时逐表核对，7,637,043 条商品及原 ID 保留。随后专用测试账号产生的新订单属于新增验收数据，不应拿切换前后的订单总数要求恒等。售价与库存均为本地模拟，不代表数据集的真实交易事实。

所有目标阶段已有对应证据：独立搜索对应搜索契约 / 实际检索 / 停机实验；商品交易拆分对应双实例 / 越权 / 故障回归；库存独立对应协议 / 丢回包 / JVM 崩溃 / 原键恢复；数据保全对应冷备恢复 / 逐表计数；最终切换对应真实 5173 交易 / 浏览器 / 履约 / 重启。源码 SHA 清单为 `FINAL-SOURCE-MANIFEST.json`；Java 运行镜像使用固定镜像 ID，不把未构建的源码修改当作已运行代码。

库存服务完全不可用时，下单目前返回非成功 HTTP（实测 500），Agent 保留 UNKNOWN 并允许同键回查 / 重试；这属于已验证的故障结果，不宣称所有依赖故障均可无感降级。导航 UI 回归按实际按钮操作；直接在已打开页面内改 hash 不属于这次已验证的导航契约。当前不宣称多机可用性、无限重试成功或真实第三方付款。
