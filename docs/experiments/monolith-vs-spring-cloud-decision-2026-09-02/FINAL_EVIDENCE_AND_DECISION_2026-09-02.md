# 模块化单体 vs Spring Cloud 当前选型裁决

## 结论

`BOUNDED_SPLIT_DEPLOYMENT_ACCEPT / HOLD_SPLIT_AS_DEFAULT`

该裁决复算 Spring Cloud V5 的同源、同机、共享 MySQL/Redis/Kafka/Elasticsearch 正式证据，
不新增或重跑 sealed attempt。

## 同源对照

- 商品详情规范化响应字节等价，单体与拆分均 50/50 请求成功。
- 20 次预热后的 50 次本地顺序请求：单体 P50/P95 为 8.078/30.897 ms；经 Gateway 的
  拆分版为 16.532/34.568 ms，即 P50 +104.65%、P95 +11.88%。
- 共享基础设施已热时应用重启：单体 ready 17.425 s；拆分三个应用按序 ready 合计
  45.068 s，即 +158.64%。
- 应用进程 1→3；直接 Compose 依赖边 4→14；应用健康检查 1→3；同时增加内部服务令牌、
  表级账号和部署控制步骤。
- 拆分的明确收益是故障隔离：Catalog 停机时，依赖目录的预览稳定映射为 503，而 Trade 与
  Gateway readiness 仍为 200。
- V5 其余正式场景验证交易、库存、幂等、Outbox/Inbox、Bulkhead 与 CircuitBreaker，10/10
  通过；200 个客户端任务争抢 50 库存得到 50 成功、150 售罄、0 超卖，但服务端购买处理器
  峰值仅为 7，不能写成 200 服务端并发。

## 决策

拆分形态在功能、隔离和可靠性合同内成立，但当前本地负载没有覆盖其网络、启动、资源与运维
成本。模块化单体继续作为默认运行方式；Spring Cloud 保留为岗位定向的可验证部署形态。
在出现独立扩缩容、团队边界或故障域需求前，不再为追求“微服务”标签强行切换默认。

## 禁止外推

不声明 QPS/容量提升、普遍性能更优、多主机生产就绪或分布式事务成立。
