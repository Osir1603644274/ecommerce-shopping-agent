## 1. 自查结论与真正修复

原 V1/V2 正式数字经独立重算保持成立，327 个原件哈希匹配；但“已有测试通过”并不等于交易边界和证据分析器没有缺陷。

| 问题 | 原始失败 | 修复和复验 |
|---|---|---|
| P1：模拟支付自调用绕过事务代理 | 无测试外层事务的 5 项对照中 2 项失败：订单拒付/Outbox 失败后支付 SUCCESS、通知 1 条残留 | `simulateSuccess` 增加事务；5 项专项及 23 项相关测试全部通过。真实 HTTP 的 422/500 故障后支付 CREATED、通知 0，重试后唯一出库 |
| P2：归档后分析器漏读认证维护事件 | 错误主要清单也可通过 | 同目录及父目录查找、冲突拒绝、相同事件去重 |
| P2：仅信任业务汇总标记 | 缺逐单证据、false 标记或篡改出库数仍可接受 | 强制逐单重算；可用时关联 SQLite，无原件明确未验证。正确归档通过，4 类负例拒绝，实际 CLI 5/5 |

原支付缺陷与 V1 初始源码相同，不归因于查询优化。报告：独立代码审计（本地材料：`evidence/audit-code/RESULT.md`）、独立证据审计（本地材料：`evidence/audit-evidence/RESULT.md`）。旧脚本、失败日志和已发布 V1/V2 原件均未覆盖。

## 2. 固定版本和验收范围

两 Java 17 实例，各 1 CPU / 512 MiB、堆 256 MiB、Hikari 4；MySQL 8.4、Kafka、本机持久仓库模拟器。每实例履约 worker 1、队列 2、租约 10 秒。配置、执行脚本副本、容器内 JAR 哈希、数据库 UUID 均随每个 attempt 保存。

实测支付修复 JAR SHA256：`f4424639ffc661363000d38cf6cce73ca1a2552ab94bf4acf2aa74482b4b80e6`。324 个源码/测试文件在审计时与清单（本地材料：`evidence/payment-fixed-source-manifest.json`）匹配；后续 V4 是另一版本，不借用本轮全部故障结论。

主要集仅为 8 个 `confirm-*-attempt001`。开发阶段、运行器修订阶段全部保留，但不并入主要数字。最终数据库导出 575 单含开发单，主要集按订单 ID 精确划分为 **287 单：248 PAID、12 CANCELLED、12 REFUNDED、15 EXPIRED**。

## 3. 异步履约、支付竞争和接管

| 场景 | 实际结果 |
|---|---|
| 停消费积压 | 60 单、132 条原始事件；消费者和 worker 关闭时 0 出库；只开消费者后 READY 36 / CANCELLED 24，仍 0 出库 |
| 双实例排空 | 两 owner 领取 24 / 18 次（含重试）；36 笔支付单各一次仓库出库，其余 24 单无出库 |
| 迟到与重复 | 从实际历史构造 7 个新事件号，按退款/取消→支付→创建逆序，各投递两遍，共 14 次；最终状态不回退 |
| 暂停后接管 | 两 owner 各领取一次，fence 1→2，仓库只出库一次；旧 worker 恢复完成后不覆盖新状态 |
| 支付与自动超时关单 | 24 单，10 PAID / 14 EXPIRED；对应签名回调 200 / 422，支付、库存、出库逐单匹配 |
| 支付原子性 | 过期拒付 422、Outbox 注入故障 500 均整体回滚；解除故障后重试及重复回调不重复出库 |

全部主要集的 **586 条原始 Outbox** 均 PUBLISHED，每条精确关联唯一且 payload 哈希匹配的 PROCESSED 履约 Inbox。248 笔支付单各一条本地 SHIPPED 尝试及一条 SQLite 出库，取消/退款/过期单零出库；各阶段库存守恒。没有仅依据全局 lag=0 判断业务成功。

暂停测试保留 `directStaleUpdateReturnObserved=false`，只证明最终状态和尝试记录，未直接捕获旧 CAS 函数返回值，也不是物理主机故障。

## 4. 持续负载下的四类故障

每场景投放 50 秒，每秒 1 个三请求写流程加 3 个分页请求；有界客户端记录接纳、排队、执行和完成时刻。四段共 **800 个计划到达、1,200 次负载 HTTP、200 单**，均完成，0 丢弃、0 flow 失败、0 HTTP 错误、0 脚本付款补偿。两实例故障前后均有成功写入。

| 故障 | 实际注入时长 | 关键原始观察 |
|---|---:|---|
| Redis 停止/重启 | 12.997 秒 | 已登录账号交易继续；故障期使用进程内限流降级，不证明全局配额仍一致 |
| 专用库存行排他锁 | 3.004 秒 | 数据库等待峰值 6；跨故障请求最长 3057.296 ms |
| 仓库提交后延迟 | 15.008 秒 | 两实例队列均峰值 2、拒绝计数增量 23 / 26；持久任务最终无丢失、出库唯一 |
| Kafka 停止/重启 | 13.174 秒 | 自有未发布 Outbox 故障期峰值 28、全阶段峰值 46；恢复后逐事件 Inbox 对齐 |

逐请求 P95/P99、故障窗口与跨窗口长请求、Prometheus 和 SQL 原始采样均在各 confirm 目录。独立报告提供复算表及原始关联：最终独立审计（本地材料：`evidence/audit-evidence/v3/FINAL_REPORT.md`）、机器结果（本地材料：`evidence/audit-evidence/v3/final-audit001.json`）。

故障释放到最终核对分别为 26.377 / 37.689 / 25.686 / 24.939 秒，包含剩余投放和轮询，只是观察上界，**不是精确 RTO**。Kafka 的 start 命令返回后约 0.992 秒首次交易成功，约 10.538 秒完成 readiness 检查；前者只说明 Outbox 允许 HTTP 交易继续，不能解释为 Kafka 已恢复。

本轮 Hikari 等待/超时观测均为 0；履约线程池排队/拒绝已测，数据库连接池耗尽不能据此标成已完成。V2 的连接等待数据另见其原报告。

## 5. 原件与局限

- 309 个原件及 SHA256（本地材料：`evidence/manifest.json`），约 344 MiB；包含失败/开发/主要 attempt、固定脚本、独立审计、实际 JAR 和最终只读 SQL/SQLite 导出，不含运行凭证。
- 全部场景含 setup/control 共 1,483 次 HTTP，其中 15 次 422、1 次 500 是预期故障拒绝；与 1,200 次持续负载零错误分别报告。
- 初次支付边界脚本把 422 写成 400，失败原件保留；随后修正合同预期。运行器经独立审查（本地材料：`evidence/audit-code/V3_RUNNER_REVIEW.md`）补门禁后冻结，再执行主要集。
- 同机、合成数据、本地支付/仓库合同、有限时间；不等于多物理机、长期容量、真实物流支付或跨系统 exactly-once。
- Redis 场景预先登录且关闭商品/店铺缓存，未覆盖故障期注册、refresh、撤销和所有 Redis 路径。
